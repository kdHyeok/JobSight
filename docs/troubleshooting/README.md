# 트러블슈팅 기록

## 목적

실제로 겪은 버그·오진·작업 도구 문제를 **문제 → 원인 파악 → 원인 → 해결 시도 → 최종 해결과 검증 → 배운 점** 순서로 남긴다.
같은 증상을 다시 만났을 때 처음부터 파지 않게 하는 것이 목적이다. 설계 결정을 되돌린 이유는 여기가 아니라 [../decisions.md](../decisions.md) 에 쓴다.

## 쓰는 규칙

- 한 사건 = 한 파일 `YYYY-MM-DD-주제.md`. 구조는 DCP 트러블슈팅 템플릿(표 머리 → 요약 → 1~6절 → 참고)을 따른다.
- 증상은 본 그대로(오류 문구 원문)를 적는다 — 검색으로 찾게 하려는 것이다.
- **오진·실패한 시도도 순서대로 남긴다.** 무엇을 보고 틀렸다고 알았는지 적는다.
- 원인 파악 흐름도와 원인 동작 그림을 Mermaid 로 하나 이상 넣는다.
- 측정하지 않은 값은 "미측정"으로 적는다. "회귀 테스트"라는 말은 수정 전 소스로 실패를 확인한 테스트에만 쓴다.
- 영역 문서(예: experiences.md 「함정」)에는 한 줄 요약과 이 폴더 파일 링크만 둔다.
- 같은 원인이 다시 나면 새 파일 대신 기존 파일에 "재발" 절을 덧붙인다.

## 관찰(조치하지 않음)

- **2026-11-03 가져오기 CREATE 의 "한 일"이 줄 단위로 나뉘지 않는다.** 행 상세 내용이 `- 인덱스 설계\n- 캐시 도입` 이면
  "이력서에서 가져오기"(서버 `ExperienceImportService`)는 `actions` 를 한 항목으로 만들고, 편집기 "경험으로 등록"
  (`experienceFromRow`·`factLines`)은 줄마다 나누고 머리 기호를 뗀다. 둘 다 저장은 정상이라 버그로 보지 않았다.
  차이는 드로어 표시와 이후 정정 판정(항목 id 단위)의 세밀함이다. 맞추려면 가져오기 초안도 `factLines` 규칙으로 나눈다.
